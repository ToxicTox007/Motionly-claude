# Motionly Data Handling, Privacy, and Retention Policy

This document details the flow of data within Motionly, including third-party providers, internal storage, data retention policies, and logging/redaction policies.

---

## 1. Third-Party Provider Data Flows

### 1.1 Groq (Whisper Transcription)
* **What data is sent:** Extracted mono WAV audio files, target transcription model, and optional language hints.
* **Why it is sent:** To generate word-level speech-to-text transcriptions and captions for uploaded video media.
* **Persisted raw payloads:** Yes, the raw transcription response (words, start/end timestamps, language, and confidence) is stored under the `transcripts.raw_payload` database column.
* **Retention policy:** Raw provider payloads in transcripts expire and are redacted after 30 days. The transcript text and word timings remain associated with the project until the project is deleted.

### 1.2 OpenRouter (AI Edit Planner)
* **What data is sent:** Transcript words and audio/visual summaries, style classification, custom prompts, style options, and target durations.
* **Why it is sent:** To generate semantic video editing plans (cuts, zoom triggers, music style preferences, and b-roll placement suggestions) via LLMs.
* **Persisted raw payloads:** Yes, a metadata summary containing token usage, validation error logs, and fallback status is stored in `plans.raw_payload`. The full raw request/response text is not persisted in the database.
* **Retention policy:** Retained with the project until project deletion.

### 1.3 Runway (Gen-3 Video Generation)
* **What data is sent:** B-roll prompts, prompt image URL/reference, and requested video duration and aspect ratio.
* **Why it is sent:** To generate premium AI B-roll scenes from images and textual descriptions.
* **Persisted raw payloads:** No raw Runway API payloads are persisted in the database. Only generated task metadata and the final video URL are saved.
* **Retention policy:** Task references and generated assets are retained with the project until project deletion.

### 1.4 Stock Providers (Pexels & Pixabay)
* **What data is sent:** Search query keywords and media size/quality preferences.
* **Why it is sent:** To search for and retrieve relevant stock video clips for B-roll injection.
* **Persisted raw payloads:** No raw stock API payloads are persisted in the database. Only retrieved media metadata and asset links are saved.
* **Retention policy:** Retained with the project until project deletion.

## 2. Internal Storage Policies

| Data Class | Purpose | Storage Layer | Retention Period |
| :--- | :--- | :--- | :--- |
| **Raw Uploads** | Original video files uploaded by users | Supabase Storage (`raw-uploads` bucket) | Retained with project; deleted 30 days after project deletion or explicit user cleanup |
| **Extracted Audio** | Temporary mono WAV files extracted from uploaded videos | Local media cache folder | Retained with project; deleted 30 days after project deletion or explicit cleanup |
| **Thumbnails & Frames** | Image frames extracted from uploaded videos | Supabase Storage (`thumbnails` bucket) | Retained with project; deleted 30 days after project deletion or explicit cleanup |
| **Transcripts** | Word timing records, caption tracks, and segments | Supabase DB (`transcripts`, `transcript_words` tables) | Retained with project until project deletion (raw provider payloads expire after 30 days) |
| **Visual Manifests** | Scene boundaries, tags, and embeddings generated by visual ML | Supabase DB (`video_manifests` table) | Retained with project until project deletion |
| **Generated B-roll** | Video assets generated by Runway or stock downloads | Supabase DB (`stock_assets`, `phase5_resources`) | Retained with project until project deletion |
| **Exports** | Final rendered output video files | Supabase Storage (`exports` bucket) | Expires and deleted 90 days after generation, or immediately upon project deletion |
| **Telemetry / Preferences** | User interaction events, feedback, and settings | Supabase DB (`ai_edit_feedback_events` table) | Retained unless user or workspace deletion triggers a purge |

## 3. Redaction and Logging Policy

To prevent the accidental leakage of sensitive keys, credentials, and user data in application logs and tracebacks:
1. **Automated Log Redaction:** All application log messages, exception logs, tracebacks, and extra metadata dictionaries are formatted using a custom `RedactingJsonFormatter` before writing to `stdout`/`stderr`.
2. **Scrubbed Fields & Secrets:** The logger and exception handling automatically redact:
   * Bearer tokens and `Authorization` headers.
   * Signed URL query params (such as `token`, `signature`, `sig`, `expires`, `access_token`, `refresh_token`, `apikey`).
   * JSON keys containing password, credential, secret, token, key, or authorization.
   * Specific AI provider key patterns (e.g. Groq `gsk_`, OpenRouter `sk-or-v1-`, Runway `sk-`).
3. **Explicit Error Scrubbing:** Exception details caught in provider HTTP adapters (Groq, OpenRouter, Runway) and worker entrypoints (`domain_job.py`, `visual_job.py`) are explicitly run through the redaction helper before being logged or raised.
