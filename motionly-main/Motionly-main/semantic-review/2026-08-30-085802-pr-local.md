# Durable generic-media deletion fencing

Task #2 moves persistent generic-media initiation into one database RPC, introduces a durable cleanup job for terminal media, and routes generic queue rows through a separate fenced acknowledgement. The lifecycle is designed to keep quota accounted until the final object and every temporary part have been physically deleted, while the B-roll and style routes verify that a session remains linked to its owner before mutating it. Watch for: **confirmed** — a pre-update retention worker can invoke the unfenced quota-deletion RPC for a generic final-object row before the generic acknowledgement verifies that all parts are gone; **confirmed** — deleting a style reference leaves it counted against the five-reference cap, so a full profile cannot add a replacement.

**Verdict**: NEEDS_CHANGES

## High-level view

Persistent initiation atomically creates the quota reservation, session, and immutable part plan. The owner link is written afterward: B-roll rereads after a failed link write, while style profiles use revision-checked updates.

Each generic cleanup job owns its part rows and final-object row; only its final acknowledgement may transition quota after sibling rows are gone. **Confirmed:** the final queue row still exposes its reservation ID to the older retention dispatcher before that acknowledgement runs.

The new database lifecycle functions acquire a linked ObjectReference before the session row, matching direct reference retirement and establishing a single reference-to-session lock direction.

Style deletion retains a tombstone in the profile payload for retryability. **Confirmed:** the admission check counts that tombstone as an active reference, consuming replacement capacity.

### Legacy retention can release generic quota before part cleanup

**Confirmed:** `motionly_enqueue_generic_media_deletion` puts `quota_reservation_id` on a generic final-object queue row. The updated `RetentionService` recognizes `generic_media_deletion_job_id` and uses `motionly_ack_generic_media_deletion_object`, but the previous dispatcher transitions quota before it calls the general acknowledgement:

```text
old retention worker
  -> delete final object
  -> motionly_delete_committed_storage_quota(queue.quota_reservation_id)
  -> motionly_ack_storage_deletion_queue(...)
```

The migration's general-ack guard rejects the generic row only at the last step. `motionly_delete_committed_storage_quota` has no pending-generic-job check, so an old worker can mark the reservation deleted while generic part rows remain queued. That permanently releases quota before the job's fence has been met.

Keep the generic final queue row free of `quota_reservation_id` so older dispatchers cannot invoke the direct transition, or move the transition behind an API that validates the generic job and is callable only from the generic acknowledgement. Not tested: a migration run using the previous retention dispatcher; `task_25_generic_media_strict_deletion_test.sql` checks general-ack rejection but not this earlier direct quota call.

### Deleted style references exhaust the five-reference limit

**Confirmed:** `delete_style_reference` marks the selected payload item `deleted` and records a timestamp but leaves it in `profile.payload["references"]`; `_init_style_reference_media` rejects any raw list with `len(references) >= 5`. A profile with five references therefore cannot replace one after deletion, even though the deleted media is already unavailable and queued for cleanup.

Count only non-deleted entries when enforcing the active-reference limit, or move deletion evidence outside the active payload. Not tested: deleting one of five references and initiating a replacement; the focused test only covers a single-reference deletion and retry.
