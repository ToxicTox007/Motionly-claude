2. Current POST /plans Flow
---------------------------
1. API receives requests at POST /projects/{project_id}/plans.
2. Validates project membership, loads transcript, and validates it is in READY status.
3. Applies Phase 5 learned template / styling preferences.
4. Identifies the effective style profile.
5. Calculates the request cache key. If cache hits and force=False, returns cached plan immediately (cached=True).
6. If cache misses, calls HttpEditPlannerProvider.create_plan(...) synchronously.
7. Under the hood, HttpEditPlannerProvider executes a synchronous httpx.post directly to OpenRouter API (https://openrouter.ai/api/v1/chat/completions) with a 45s timeout.
8. This blocks the main FastAPI event loop thread for up to 45 seconds on LLM network latency.
9. Represerves/repairs the LLM response, falling back to a deterministic fixture planner on validation failure.
10. Writes the plan object synchronously to the database via SupabasePlanRepository.create_plan (patching older versions).
11. Records SLO metrics, token usage costs, and returns the response.

3. Current Queue Architecture
-----------------------------
- Powered by BullMQ and Redis backend.
- Node.js worker loop (apps/worker/src/worker.mjs) processes tasks from Redis.
- When jobs are dispatched, the worker spawns a persistent Python worker subprocess (apps/api/app/workers/domain_job.py).
- Python processes call internal HTTP job execution routes (or invoke handlers via internal_jobs._execute_job()).
- Heavy jobs (transcription, preprocessing, rendering) route via isolated queues.

4. Whether PlanQueue Exists
---------------------------
- Yes, PlanQueue is declared in apps/api/app/services/queue.py.
- Queue Name: "planning"
- Job Kind: "edit_plan"

5. Existing Worker Handler Status
---------------------------------
- Bypassed/Incomplete: The job kind "edit_plan" is dispatched by Node to domain_job, but in Python's internal_jobs._execute_job(), it is not handled and defaults to:
  {"message": "Queue item was already completed synchronously by the API.", "skipped": True}

6. Existing Status/Polling Pattern
----------------------------------
- Asynchronous tasks like transcription write a database record with status="queued" and submit the job to BullMQ, returning a stub immediately.
- The client polls GET /projects/{project_id}/plans/transcript to monitor progress.
- No polling pattern currently exists for edit plans.

7. Frontend Assumptions That Must Change
----------------------------------------
- Frontend components (ai-step.tsx, editor-client.tsx, ScalePanel.tsx) expect the POST /plans call to return the full EditPlanRecordSummary immediately.
- If the endpoint returns 202 Accepted, callbacks fail with "TypeError: Cannot read properties of undefined (reading 'id')".
- Client must catch 202 status, trigger a loading screen, poll a job status path, and only invoke callbacks once the job transitions to succeeded.

-----------------------------

- Safe Sync Route Exclusions: Restore snapshot and compile timeline endpoints can remain synchronous because they do not query LLMs.
